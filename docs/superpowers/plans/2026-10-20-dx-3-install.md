# agent-forge DX — Sub-project 3: Guided install Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One command on the developer's laptop, `forge install`, installs or updates a host (the local Lima VM, or a remote VM) and ends with herdr attached; `forge open` attaches herdr afterwards.

**Architecture:**
- **Two sides, one codebase.** `cli/lib/side.ts` tells the laptop from the host and gates every command to its side. The laptop commands live in `cli/lib/commands/install.ts` and `cli/lib/commands/open.ts`, and their building blocks in `cli/lib/laptop/`.
- **Laptop state.** `~/.config/agent-forge/` on the laptop holds `hosts.json`, one directory per host (`hosts/<name>/inventory.yml`, the chosen key's `.pub`), and forge's own `known_hosts`. forge writes its SSH blocks to `~/.ssh/config.d/agent-forge`, included from `~/.ssh/config`.
- **The host is driven over SSH.** Every host-side step (git identity, `claude auth login`, `forge setup`, `forge image build`) runs through the forge user's SSH alias. One new host command, `forge image commit`, tells the laptop which commit `agent-base` was built from.
- **GitHub's host keys** are fetched over HTTPS by the playbook, on the controller, and written to the forge user's `known_hosts` on the host.

**Tech Stack:** Node 24 (type stripping, `node --test`), TypeScript (`npm run check`), OpenSSH, Lima ≥ 2.1.2, ansible-core ≥ 2.20, herdr 0.9.5.

**Spec:** `docs/superpowers/specs/2026-10-20-dx-chapter-design.md`, section "Sub-project 3: guided install", plus "Decisions", "Non-goals" and "Anti-goals". Read it first.

## Global Constraints

- Prerequisites: `limactl` 2.1.2 or newer (local only), ansible-core 2.20 or newer, `herdr`, `git`, an SSH agent holding at least one key; Node 24 is checked by `cli/forge`.
- Host names: `forge-local` for the Lima VM; `forge-<name>` for a remote VM. A name matches `^forge-[a-z0-9][a-z0-9-]*$`.
- `forge install` never installs a package, never edits `~/.ssh/config` beyond one `Include config.d/*` line added at its top after a confirmation, and writes nothing outside its own directories (`~/.config/agent-forge/`, `~/.local/share/agent-forge/`, `~/.ssh/config.d/agent-forge`, and the `~/.local/bin/forge` link after a confirmation).
- `forge install` acts only on hosts it created (listed in `hosts.json`).
- One host, one laptop: the generated inventory's `ssh_keys` holds exactly the chosen key.
- The admin connection offers exactly one key (`IdentitiesOnly=yes`): sshd allows two attempts, and fail2ban bans on `public`.
- GitHub's SSH host keys come from `https://api.github.com/meta` (`ssh_keys`), never from the repository; a failed fetch stops the run, never falls back to trust-on-first-use.
- No personal value (login, host, path, identity, address) in code, tests or docs; examples use `alice`, `203.0.113.10`, `forge-acme`.
- Every path forge reads or writes on the laptop has an environment override for tests (as `cli/lib/paths.ts` does): `FORGE_HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, plus `FORGE_SSH_DIR` (new) and `LIMA_HOME`.
- Commits: conventional messages. The maintainer signs with a YubiKey; if they are not present, stop before committing and ask.
- Task 12 (README) starts only once moroine/agent-forge#76 is merged into `main` (it rewrites the same README lines): merge `origin/main` into the branch first.

## Review Focus

1. **An agent holding several keys, or the GitHub key in a non-default agent** (`IdentityAgent` set only for `github.com`): the key list must come from the agent ssh really uses for GitHub, and the forge block must carry that agent, or the host's clone fails later with `Permission denied (publickey)`. → Task 4, test `keys are listed from the agent ssh uses for github.com`.
2. **A re-run after a failure at each step** (playbook failed, `claude auth login` interrupted, image build failed): the next `forge install` resumes without re-asking answered questions or recreating the VM. → Task 11, test `a re-run after a failed playbook resumes at the playbook with the saved answers`.
3. **A Lima VM that `hosts.json` lists but `limactl` no longer has** (the developer deleted it by hand): `install` says so and offers to forget it and start over, rather than failing on SSH. → Task 5, test `a listed Lima VM that is gone is offered to be forgotten`.
4. **`~/.ssh/config` already has an `Include` covering `config.d/*`, or has `Host *` blocks before forge's include**: no second `Include` is added, and the existing file is byte-for-byte unchanged except for that one line. → Task 7, tests `an existing Include is detected` and `the Include goes above the first Host line`.
5. **An image built from a commit the laptop's checkout does not know** (built from another clone, or before a rebase): `install` asks before a 10-minute rebuild instead of rebuilding or skipping silently. → Task 9, test `an image commit unknown to the checkout asks`.

### Task 11: `forge install` and `forge open`

**Files:**
- Create: `cli/lib/commands/install.ts`, `cli/lib/commands/open.ts`
- Modify: `cli/forge.ts` (parse `--remote <address>` and `--host <name>`, both strings, only for `install`/`open`; dispatch)
- Test: `tests/install.test.ts`, `tests/open.test.ts`

**Interfaces:**
- Consumes: Tasks 2 to 9.
- Produces: `cmdInstall(ctx: Context, opts: { remote?: string; host?: string; checkout?: string }): Promise<number>`, `cmdOpen(ctx: Context, opts: { host?: string }): Promise<number>`.

The run, in order; each step is recorded in `host.done` when it succeeds and skipped on a re-run when recorded (the playbook, `setup` and `image` steps always run again on a re-run of a finished host, since a re-run is an update):

1. **Which host.** No option → `forge-local` (kind lima). `--host <name>` → that listed host. `--remote <address>` → the listed host with that address, or a new remote host.
